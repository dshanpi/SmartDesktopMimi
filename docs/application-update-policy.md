# SmartDesktopMimi 分层、版本配对与发布门禁

规范编号：`MIMI-UPDATE-001`；版本：`1.0.0`；确认日期：2026-10-10。

用户已确认：SmartDesktopMimi 上层应用独立开发、独立发布；硬件平台通过统一接口
接入。首个平台为 A133，后续包括 T527、RK3576。应用更新与系统更新分开，必须防止
板型、版本和依赖错配。本文件是这些要求的统一工程约束，适用于开发、构建、发布、
在线更新、离线安装和恢复工具。

**状态：要求已确认，更新器、匹配与发布门禁已有开发候选实现，尚未上线。**
当前实现和未完事项见 [实现与验收](update/IMPLEMENTATION.md)。拆仓、正式产物发布及
新应用升级实机验收尚未完成，不能把主机测试通过视为平台验收通过。
已有 A/B 系统 OTA 与 `.aitapp` 安装器不等于桌面自身升级机制。

## 1. 分层和代码归属

```text
统一桌面、内置应用、Web/CLI
          ↓
上层业务用例与领域逻辑
          ↓
版本化 Ports / IPC 契约、能力查询
          ↓
平台 Provider / 硬件服务 / 厂商适配
          ↓
板级系统、驱动、内核、Bootloader
```

- 上层依据接口和能力使用硬件，不以 SoC 分支、设备节点或厂商 SDK 实现业务。
- A133、T527、RK3576 各有自己的 Provider、板型配置、工具链、运行依赖及验收记录。
  上层源码统一不代表不同平台共用同一二进制包。
- 当前 `lv_backend` 混有业务与硬件服务。首期固定其硬件行为，梳理业务归属后逐项迁移，
  不因目录或进程名称而把整个后端认定为可随桌面替换。
- 现有 V1 桌面协议需要显式冻结其消息编号、布局和语义；V2 框架当前仅接通
  `system.ping`、`platform.describe`，不能宣称全部应用操作已经迁移。
- 接口增加保持兼容；破坏性修改提升契约主版本，并提供过渡适配和兼容测试。
  新应用至少验证所声明支持的已发布平台，不能只测试同时编译的新前后端。
- 独立应用仓库保留业务、资源、测试和发布工具；底层仓库保留硬件实现与系统集成。
  最终仓库地址在拆分时登记，不在本规范虚构已存在的仓库。

## 2. 两条发布线

| 发布类型 | 内容和边界 | 必需产物 |
| --- | --- | --- |
| `application` | 桌面、内置应用、上层业务、字体资源及应用私有依赖；不得覆盖内核、驱动、共享厂商库、平台服务或设备身份 | 应用升级包、源码包、兼容性清单、签名、校验和、构建锁定与验收记录 |
| `system` | 内核、驱动、Bootloader、板级配置、基础运行库、平台服务及更新器基础设施 | 对应板型的完整镜像；提供系统 OTA 时附系统升级包；系统构建锁定、签名/校验、源码来源与验收记录 |

纯应用发布不要求新系统镜像、新硬件提交或新硬件标签。系统镜像必须记录出厂预装的
应用版本、提交及包哈希。应用更新需要新的平台能力或基础运行库时，应声明前置系统
要求，并通过独立系统发布满足；不得在应用包内夹带底层替换来绕过系统门禁。

首个支持应用升级的系统基线需集成独立更新器、可信公钥、平台身份和版本启动入口。
旧设备不满足前置条件时明确提示所需系统版本，不尝试强制安装。

## 3. 设备与产物身份

以下为后续机器可读清单的必需语义，尚不是已接通的 JSON schema。实现时必须建立
严格 schema、生成器和统一匹配库，不能仅新增字段却不执行检查。

| 身份/约束 | 必需内容 |
| --- | --- |
| 产品 | `product_id`，防止不同产品之间误装 |
| 硬件目标 | `platform_id`、`soc_id`、`board_id`、允许的 `hardware_revision`；必要时包含内存、存储、显示/触控等变体身份 |
| 二进制运行环境 | CPU 架构、指令集基线、位数/字节序、ABI、libc/动态加载器及所需共享库或运行时契约 |
| 平台软件 | 系统版本/基线 ID、平台 Provider 版本、Ports ABI 与 IPC 契约版本；已知问题版本排除项 |
| 应用 | 应用版本、完整提交、发布类型、稳定/测试通道、包格式版本、升级序号 |
| 安装要求 | 最低更新器版本、所需能力、用户数据 schema 的读取/写入/迁移兼容范围、磁盘空间要求 |
| 系统包附加要求 | 启动方式、分区布局、存储介质/容量及刷写目标，Bootloader 兼容要求 |

设备身份由系统在制造或受控平台安装时写入，并与可读取的板级身份核对。应用升级包
不能改写身份或把自身清单当成设备身份来源。仅有 SoC 名、`uname -m` 或人工输入的
包文件名不足以判定匹配。身份缺失、冲突、无法验证时拒绝激活更新，进入明确的诊断流程。
硬件修订暂时没有可靠识别方法的设备，须先完成受控登记，不默认匹配全部修订。

目前 `platforms/a133/platform.json` 为 A133/B6 参考配置，仍须补齐上述身份和验收；
`platforms/rk3576/` 为骨架。现有 `platforms/a527/` 不是 T527 的可用实现或兼容证明。
T527 必须独立登记；未经芯片、板型、SDK 与实机证据确认不得设别名或合并目标。
`reference`、`skeleton` 和文件存在均不等于已通过应用更新验收。

## 4. 匹配规则：所有条件同时成立

一个 Release 可包含多个目标包。每个包的 `targets[]` 必须逐项记录完整的允许组合：
产品、平台、板型/修订、二进制运行环境、平台接口及系统约束。设备须完整满足其中
**同一个目标条目**，同时满足包级依赖和升级要求，才可安装。

- 不得将多个平台、多个板型和多个版本范围分别取并集后任意组合，造成未验证的交叉匹配。
- CPU 都是 `aarch64`、版本号相同或文件名相似，不构成跨板兼容证据。
- 只有逐个目标通过验证的包才能声明多板通用；默认按平台和板型产出独立包。
- 未知字段涉及必需约束、未知清单版本、空目标、缺字段、未知版本或范围解析失败均拒绝。
  不得自动退化为通配符、跳过检查或选择“最接近”的板型。
- 应用/系统版本独立编号，SemVer 按数值和预发布规则解析，不做字符串大小比较。
  兼容范围与版本命名空间明确；不能用应用版本代替平台接口版本。
- 仅从设备所选通道筛选兼容候选；默认 stable，测试通道必须显式选择。
  GitHub 的 latest 标记不代表可安装；候选清单须验签后才能用于安装决策。
- 目标不符时在停止应用或写入生效位置之前拒绝，并给出实际值、要求值和失败原因。
  命令行、离线导入与网页入口必须调用同一套校验，不能提供日常强制绕过开关。

## 5. 构建追溯与安装兼容分别记录

`release-lock.json` 记录规范版本、发布类型、应用标签和完整 SHA、工具链/sysroot
标识与哈希、依赖锁定、目标配置摘要、构建命令和包哈希。SDK 本地补丁、配置、未跟踪
构建输入必须保存；只记录提交号或修改文件名不足以声称可复现。

应用锁定记录构建和实测使用的平台基线；安装则依据签名兼容清单的接口及运行依赖范围，
不要求设备硬件仓库提交必须等于应用构建时记录的提交。系统锁定另外固定硬件提交、
完整 SDK 组件清单、镜像哈希、分区配置和预装应用身份。

包、清单、锁定记录、源码和验收证据中的目标与版本必须一致。验收报告绑定实际测试
包的 SHA-256、设备目标和系统基线，修改二进制后不能沿用旧通过记录。固定运行时依赖
的分发来源与许可信息；不得把秘密、设备凭据或未获授权的厂商输入放入公共包。

## 6. 更新事务、数据与双向回退

- 使用独立于桌面的更新服务；先完整下载并验证可信签名、大小、哈希、目标、依赖和空间，
  再解包到隔离版本目录。检查路径穿越、链接逃逸和解压资源上限。
- 签名覆盖包哈希、目标、版本和兼容条件；可信公钥由平台管理，普通应用包不能自授信。
  定义密钥轮换、撤销及清单防重放策略。普通更新不得自动降级。
- 保留已验证旧版本，采用原子切换、必要的文件/目录持久化与事务日志。下载、解包、切换、
  首次启动每一步断电后都能确定恢复到哪个完整版本。
- 启动成功至少要求桌面就绪、主循环响应、后端契约握手和关键状态可读；不能仅以 PID
  存活提交升级。失败回到本次事务记录的已验证版本，不无限重装已失败的候选。
  自动回退是受限恢复路径，不能成为安装任意旧包的降级入口。
- 用户配置、媒体、扩展应用数据和工厂凭据独立持久保存，不由升级包覆盖。数据迁移须
  有旧版本可读的兼容方案或可恢复快照；不可逆迁移未准备恢复路径时阻止升级。
- 应用更新与系统 OTA 共享互斥事务。系统升级、系统回退也要检查持久分区中的当前应用
  是否兼容目标系统；必要时一起选择已验证应用版本。不能只保证“新应用配旧系统”，
  却让系统 A/B 回退后加载不兼容的新应用。
- 默认自动检查并提示；自动下载/空闲安装为可配置策略，不中断语音或设备控制任务。
  网络失败保留当前版本；离线包仍执行全部信任与兼容检查。

## 7. 三处强制门禁与发布状态

| 阶段 | 必须检查 |
| --- | --- |
| 构建/打包 | 源码与标签、依赖和平台输入固定；检查 ELF 架构/加载器/链接依赖；包内容白名单；目标清单一致；生成签名与哈希 |
| 上传/公开 | 核对源提交和远端标签、锁定关系、每个目标的验证记录；上传草稿后重新下载远端资产复验；全部通过才推广 |
| 设备安装/激活 | 核对可信签名、真实设备身份、完整目标组合、平台/运行库/数据兼容及更新器要求；激活前在事务锁内重查，禁止绕过 |

| 状态 | 门禁 |
| --- | --- |
| Draft | 记录真实 passed / not_run / failed；缺资料、构建失败、匹配失败、已知升级或硬件失败只留草稿/本地工程包，不供设备自动安装 |
| Pre-release | 产物完整、签名/匹配/构建与自动测试通过；来源与分发资料齐备；允许明确列出尚未执行的实机项目，不允许已知失败；仅显式测试通道可选 |
| Stable | 每个宣称支持的目标及必需升级路径全部 passed，包括实机升级、回退、断电恢复和数据保留；无未解决的发布阻断项 |

发布后不移动标签、不覆盖同版本资产；修订需新版本。某板型未通过时，可以移除该目标
后重新生成清单和发布证据，只发布已验证目标，不把 A133 的通过结果复制给 T527/RK3576。
设备默认不会收到不匹配或未验收的 stable 候选。

## 8. 必需验收矩阵

每个目标记录设备板型/修订、系统基线、当前应用、目标应用、包哈希及各项结果：

1. 匹配的正常升级；所声明兼容范围的旧平台、新平台和边界版本验证。
2. 错产品、错 SoC、同架构错板、错硬件修订、缺身份、错 libc/加载器、缺能力、过旧
   更新器和不兼容接口，全部在激活前拒绝；多个目标条目之间不能交叉拼接通过。
3. 清单篡改、签名错误、包损坏、旧清单重放、路径逃逸、解压超限、空间不足和下载中断。
4. 下载/解包/切换/健康检查期间断电或杀进程；新应用启动失败和无响应；回退后可继续使用。
5. 配置、媒体、扩展应用、Wi-Fi/蓝牙配置及工厂凭据保留；数据迁移后仍能按约定回退。
6. 系统升级/回退与应用版本的双向配对；并发更新被拒绝或串行化。
7. 冷启动、顶栏、设置、应用列表、返回导航、显示/触控及所声明提供的硬件功能。
   “点击设置打开语音助手”一类真实导航错误必须作为回归项；截图不替代实际输入验收。

主机 CI 不能伪造实机 passed。当前设备尚有未解决的稳定性现象，相关目标在完成复测前
不能宣称通过新的正式发布门禁。

5. 按矩阵实测首个系统基线和首个应用升级版本，门禁通过后才能声明上线。

通过修改新规范、平台别名或验证文本，把历史未验证产物改写成已验收。
